- 실제 PC/외부 도구 실행 권한 확대: 기존 기본 거부 유지. 새 도구 활성화는 도구별 허용 범위·샌드박스·반환 증거에 대한 별도 승인이 필요하다. 이번 단계는 등록된 도구의 현재 승인 검증과 제한된 dispatcher이며 기본 실행기는 없다.
- 운영 v6 이행: 승인 전에는 실행하지 않는다. 새 빈 승인 증거 테이블만 추가하며 운영 백업·오프라인 전환은 후속 승인 후 수행한다.

## P1-06 후속 정책

- 체크포인트 정리/보존기한: 기존 안전 제한을 재사용해 사용자별 최대 16개 작업·작업당 최대 128회 상태 전이를 유지한다. 자동 삭제/기록 덮어쓰기 없이 한도 도달 시 중단한다. 보관/정리 UI나 한도 확대는 후속 설계로 남긴다.
- 만료·철회·정책 변경으로 이전 계약 승인이 무효해지면 그 계약을 재사용하지 않는다. 새로운 승인 참조를 포함한 새 계약/작업을 만들고 이전 기록은 보존한다. 유효한 기존 계약의 pause/interrupted 재개만 현재 승인 확인 후 가능하다.

## P1-07 실행 경계

- GPU: 기존 GPU 측정/admission 수식을 재사용한다. 로컬 Ollama 프로세스의 물리적 VRAM hard cap이나 시스템 전체 격리는 제공하지 않는다. 실제 측정이 없거나 한도를 넘으면 실행/결과 사용을 차단한다. 전체 모델 unload, 설정 변경, 새 모델 설치는 수행하지 않는다.
- runtime callback: 신뢰된 서버가 등록한 취소 가능한 bounded I/O만 연결한다. 임의 동기 Python/호스트 명령·모델 제공 callback은 허용하지 않는다. 실제 로컬 위임/독립 runner 연결은 P2 승인 범위에서 진행한다.
- 불명확한 timeout/중단: 예약을 보수적으로 유지하고 자동 재실행하지 않는다. 기존 결과의 실제 완료 여부를 새 실행 성공으로 추정하지 않는다. 운영자의 실제 프로세스 정리·운영 전환은 별도 승인이다.

승인된 구현/단위/회귀·CI 준비는 계속 진행했고, 아래 항목이 없어 실제 A/B 완료·개선 판정·P2-E dev 병합만 보류한다. 승인이나 모델 점수를 임의로 만들지 않는다.

2. **별도 Codex 직접 기준선**: 공개 10과제 패키지 `/home/serveradmin/role-ai-worktrees/docs/p2-e-public-baseline-3w6w09pq/README.md`. seed7, 구현 digest `cd550f91aaef47d59c7127d787d6e3abd9ce82ae0418fcc1b0662ab0e0153d05`. 공개 목표·stub·공개 테스트만 포함하며 정답/숨김 사례 없음. 새 독립 세션에 이 폴더만 제공하고 과제별 solution.py만 작성한다. 현재 세션은 oracle을 작성/열람했으므로 공정한 직접 기준선 답안을 작성하지 않는다. 새 AI agent/유료 API를 자동 실행하지 않는다. 파일이 바뀐 새 소스에서는 패키지를 새로 export해야 한다.

### 준비된 실행 경로

P2-E 브랜치에서 기존 가상환경을 사용한다. 아래 명령은 Docker 권한과 기존 설치 이미지가 제공된 **격리 개발 환경**에서만 실행한다. 모델/이미지 신규 설치 명령이 아니며 사전검사를 통과하지 못하면 중단한다.

```bash
python -m role_ai.task_delegation_lab --task budget-check --seed 7 --model qwen3.5:4b-q4_K_M --model-digest d8b0f5e9760cd1682034f292d7ef72ec46f432149be0df7574bf2d6e92e38c04 --image python:3.12-slim@sha256:aa943ce411423c7582288f18707ff66eddcbaeb510502d747a72aeb34f30d159 --windows-loopback
python -m role_ai.task_baseline --public-root /home/serveradmin/role-ai-worktrees/docs/p2-e-public-baseline-3w6w09pq --task budget-check
```

각 과제마다 같은 seed/image/예산/기기에서 반복하고 실패·중단도 보존한다. baseline 명령은 후보를 독립 채점할 뿐 작성 주체·Codex 토큰을 추정하지 않는다. `--producer-receipt` 없이는 실제 Docker 통과라도 unverified_submission으로 실제 A/B 집계에서 제외한다. 직접 기준선 제출물은 별도 context 검토 수신(format role-ai-codex-baseline-context-v1, task_id/candidate_sha256/public_manifest_sha256/context_review_sha256)과 결합해야 실제 작성 근거를 기록할 수 있다. checksum은 인증/실행 권한이 아니다.

`python -m role_ai.task_comparison compare --image <동일 digest> --metrics <private metrics.json ...>`는 실제 paired10과제와 검토/CI·사용량 근거가 부족하면 exit2로 미완료/불충분을 보고한다. `--regression-receipt`는 구현 digest/head SHA 및 최종6 CI job 수신, `--protocol-receipt`는 public_manifest/context_review/hardware_conditions 원문 hash를 받는다. 이 자료가 있다고만 쓰지 말고 실제 원문을 확인해야 한다.

현재 실제 실행한 비교 명령은 A0/B0/coverage false/개선 false/절감률 null, exit2로 올바르게 미완료를 반환했다. P2-E는 실측·검증 근거 부족 상태로 Draft PR을 유지하며, dev 병합 및 Phase 3 착수를 완료로 보고하지 않는다.

### 2. Docker 접근 문제: 추천안과 대안

**우선 추천: 이미 존재하는 전용 개발 Docker 환경 재사용.** 운영 daemon/DB/volume과 분리된 환경에서 기존 제한된 runner를 실행한다. Windows Ollama는 설치된 동일 모델을 유지한다. 환경이 달라지면 A/B 모두 그 평가 환경을 기준으로 다시 조건을 고정하며, 이전 GPU/시간 수치를 그대로 이어 붙이지 않는다. 사용할 수 있는 개발 환경이 실제로 있는지는 확인이 필요하다.

**개발 환경이 없다면 조건부 대안: 사용자 전용 Rootless Docker 검토.** daemon과 컨테이너를 일반 사용자로 실행하는 방식이다. 설치·사용자 서비스·필수 시스템 설정이 필요할 수 있으므로 별도 변경안을 검토한 뒤 승인 범위에서 준비한다. 운영 Docker를 정지/재시작하거나 전역 Docker context를 바꾸는 절차가 나오면 적용을 멈추고, 운영과 분리된 개발 환경 방안으로 돌아간다. 기존 운영 서비스를 중단하는 설치 절차를 그대로 따르지 않는다. [Docker Rootless 공식 문서](https://docs.docker.com/engine/security/rootless/)

Rootless라는 이유만으로 기존 sandbox와 동등하다고 판정하지 않는다. 공식 문서에 따르면 cgroup 자원 제한은 cgroup v2/systemd 조건과 controller 위임에 영향을 받으며, 조건이 맞지 않으면 관련 실행 옵션이 무시될 수 있다. 메모리·CPU·프로세스 수 제한, network none, 읽기 전용 파일 시스템, 비root 실행, timeout/cleanup을 실제로 확인해야 한다. 적용되지 않는 제한을 성공으로 처리하거나 보안 옵션을 제거해 통과시키지 않는다. [Rootless 자원 제한 공식 문서](https://docs.docker.com/engine/security/rootless/tips/#limiting-resources)

**추천하지 않는 빠른 우회:** 운영 Docker 소켓의 전체 쓰기 허용, 현재 계정의 운영 docker 그룹 추가, 무제한 sudo, privileged 컨테이너. docker 그룹 접근은 daemon을 통한 root 수준 권한을 부여하므로 단순한 로그/테스트 편의 설정으로 취급하지 않는다. [Docker Linux post-install 공식 문서](https://docs.docker.com/engine/install/linux-postinstall/)

현재 코드의 연결 제약도 먼저 해결해야 한다. `role_ai/task_delegation_lab.py:102`의 `synthetic_environment(..., socket=None)`는 별도 socket을 받을 수 있지만, `:154`에서 기본값은 `/var/run/docker.sock`이며 `:191`부터 정의된 CLI에는 socket 옵션이 없다. `task_baseline.py`의 CLI에도 socket 옵션이 없다. 따라서 `DOCKER_HOST`나 Docker context만 바꾸면 평가기가 새 endpoint를 사용한다고 안내하지 않는다. 기존 runner는 Settings에 지정된 socket을 사용한다.

별도 endpoint가 선택된다면 **후속 구현 제안**은 두 평가 경로에 동일한 명시적 로컬 Unix socket 선택을 연결하는 최소 변경이다. 허용 endpoint·소유권·심볼릭 링크·실제 자원 제한을 검증하고, 기본 동작/기존 승인·scope·sandbox 정책은 유지한다. 원격 TCP/SSH 실행·전역 설정·모델이 지정하는 socket은 도입하지 않는다. 이 문서 갱신에서는 코드를 구현하지 않았으며, 해당 변경 범위는 선택한 환경과 함께 확정해야 한다.

### 3. Codex 직접 기준선: 기존 VS Code 방식 유지

추천안은 기존 공개 패키지를 별도 평가 세션에 제공하는 것이다. 이전 Role-AI 대화, 원본 저장소, 정답/숨김 평가 코드, 현재 세션의 해설·답안은 전달하지 않는다. 동일한 공개 목표와 테스트를 사용하고, 각 과제의 solution.py만 제출한다. 모델 교체·신규 설치·새 유료 API는 필요 조건으로 두지 않는다.

작업 폴더를 바꾸거나 새 대화를 시작한 것만으로 OS 수준 격리나 정답 미열람을 증명했다고 표현하지 않는다. 실제 사용 가능한 접근 제한과 읽은 파일·작업 기록을 확인한다. 충분한 제한/검토 자료를 확보할 수 없다면 해당 제출물은 탐색용 pilot 또는 unverified_submission으로 보존하고, 공식 A 기준선으로 승격하지 않는다.

제출 뒤에는 Codex가 주장한 점수 대신 기존 독립 Docker grader로 채점한다. public fixture 원문, candidate hash, manifest hash, context 검토 원문의 hash를 결합해 작성·검토 근거를 남긴다. hash만 만들거나 검토했다고 적는 것으로 원문 확인을 대체하지 않는다. 현재 oracle을 본 세션이 직접 답안을 작성하는 방안은 공정한 기준선의 대안으로 사용하지 않는다.

### 4. Codex 토큰 사용량: 측정 가능한 것부터 분리

**추천안:** 실제 작업 구간에 대응하는 공식 클라이언트/API 사용량 원문이 제공되는 경우에만 사용한다. 현재 VS Code 환경에 그런 작업별 자료가 제공되는지는 미확인이며, 지원되지 않는 내부 API·확장 기능·로그 해석을 새로 가정하지 않는다. 자료 수집을 위해 새 유료 API를 호출하지 않는다.

측정 범위는 A/B 모두 작업 정의부터 최종 검토까지로 미리 고정한다. B의 Codex 비용에는 계약 작성·오류 개입·최종 검토도 포함하며, 로컬 LLM 토큰만 보거나 Codex 비용을0으로 놓지 않는다. 전체 계정/여러 세션의 합산 수치를 특정 과제의 수치로 나누어 추정하지 않는다. 입력/출력/캐시 등 서로 다른 범주가 제공되면 같은 정의로 비교하고 원문 구분을 유지한다.

**사용량 원문이 없을 때의 권장 진행:** 품질·시간·Ollama backend 토큰·장치 GPU 관측·반복/실패 결과부터 평가하되, Codex 토큰과 절감률은 null로 남긴다. 문자열 길이/로그 압축 비율은 별도의 출력량 지표로만 표시한다. 원문이 없는 상태에서 이미 정한 토큰 절감 검증 조건까지 충족했다고 판정하지 않는다.

사용자 판단은 두 가지다. 실제 작업별 사용량 근거를 확보할 때까지 전체 성능 완료를 보류하거나, 미측정 상태의 품질/시간 보고를 허용하도록 완료 기준을 명시적으로 조정한다. 후자는 **기준 변경 제안**이며 현재 확정된 정책이 아니다. 현 비교 도구는 Codex 사용량이 없으면 개선 판정을 보류하므로, 기준 변경 시 보고/완료 판정의 수정 범위도 별도 검토한다. 현재 CLI에는 임의 Codex 사용량을 자동 계측·주입하는 기능이 없으며, 자료 확보 후 실제 receipt 연결 방식과 값의 원문 결합도 확인해야 한다.

### 5. 평가 실행과 최종 처리 추천

1. 선택한 개발 환경에서 기존 digest-pinned 이미지 존재와 제한 집행을 확인한다. 설치가 필요하면 변경 범위를 따로 정한다. 현재 공개 패키지의 구현 hash와 실행 소스가 일치하는지 확인하며, runtime 코드가 바뀌면 새 패키지/프로토콜을 만든다.
2. smoke는 A/B 각 한 과제로 실행 경로를 확인하는 용도로만 사용한다. smoke 결과를 유리하게 골라 공식10과제 결과에 섞지 않는다.
3. 정식 비교는 같은10과제·seed·이미지·예산·독립 채점 방식 및 사전에 정한 동일 반복 수로 수행한다. 우선 1회씩 전체 실행하고, 결과 안정성 판단이 필요하면 양쪽 모두 같은 수로 확대한다. 성공한 실행만 재선택하지 않는다.
4. GPU를 사용하는 다른 작업과 겹치지 않는 평가 시간을 확보한다. 샘플 VRAM은 장치 전체의 관측값으로 표시한다. 준비/추론/채점/사람 대기 시간의 경계를 맞추지 못한 구간은 직접 속도 비교에서 분리하거나 미측정으로 남긴다.
5. 실제 전체 성공률·채점 coverage·미측정·실패/회복·사용량·시간을 비교한다. 품질 회귀가 있으면 낮은 토큰 수만으로 개선으로 판정하지 않는다. 참조 코드/스크립트 모델/계획 응답1회의 수치는 실제 코딩 성능으로 집계하지 않는다.
6. 실행 근거와 10 Pass를 보고서에 반영한다. 코드가 바뀌었으면 필요한 테스트와 최종 head의 CI를 다시 확인한다. 변경이 없는 기존 통과 검사를 이유 없이 반복하지 않는다. 실측/승인 조건 미충족 시 PR #47은 Draft/미병합으로 남기며, 조건을 충족한 후에만 기존 승인 범위의 dev 병합을 진행한다.

## 추천안 진행 수신 — 소켓 연결 구현 및 환경 준비 (2026-10-31 KST)

사용자의 "괜찮네. 그대로 진행하고 남은 작업 이어서 해줘"에 따라 추천 순서의 개발 환경 확인·명시적 socket 연결을 진행했다. 기존 추천 문단은 당시 제안 기록으로 보존한다. 실제 진행/확정 범위는 이 절을 우선 참고한다. 완료 기준은 유지하며 운영 권한·서비스 변경이나 새 모델/유료 API로 우회하지 않는다.

- 새 `--socket` 옵션을 위임 lab과 직접 기준선 채점 양쪽에 연결했다. explicit 값은 private 사용자 소유·정규 경로의 Unix socket만 받는다. 링크/원격 URI/공개 디렉터리/다른 소유자/세계 공개 socket은 거부한다. 선택값은 모델 출력에서 받지 않는다.
- socket inode/소유권·parent identity를 승인 환경에 결합했다. 소켓 교체/재시작 후 기존 승인은 결과 사용을 차단하며 새 검증·승인이 필요하다. 새 explicit endpoint는 rootless/cgroup-v2/systemd와 기존 CodeExecutor의 메모리/swap/CPU/pids/seccomp/image 사전검사를 통과해야 한다. 메타데이터 통과만으로 실제 자원 제한 집행을 완료했다고 판정하지 않는다.
- 기본 서버/CI endpoint 정책은 유지한다. 전역 context/환경변수/권한/운영 daemon 변경은 없다. 새 CLI가 root 소유 운영 socket을 새로 허용한 것이 아니다.
- 실제 환경 조사: default 운영 context/socket 하나, 사용자 Rootless 서비스·도구 없음. subuid/subgid65,536범위와 cpu/memory/pids 위임은 존재, user namespace 단독 probe exit0. 관리자 패키지 사전 모의 실행은 uidmap/libsubid4 신규2·upgrade/remove0을 표시했다. 실제 설치/서비스 생성은 미수행이다.
- 관리자 인증을 대신할 수 없어 `newuidmap/newgidmap` 준비가 필요하다. 운영 Docker를 중단하지 않는 구체적 준비 범위·모의 실행·중단/보존 조건은 [ROOTLESS_SETUP_PLAN.md](ROOTLESS_SETUP_PLAN.md)에 정리했다. 사용자가 이미 허용한 별도 개발 daemon을 제공하면 그 환경을 우선한다.
- 공식 사용량 이벤트 경로는 확인했다. 실제 VS Code 작업별 원문 확보와 동일 비용 구간 검토는 아직 필요하다. [CODEX_USAGE_PROTOCOL.md](CODEX_USAGE_PROTOCOL.md)에 공식 출처와 null 유지 조건을 정리했다. 실제 대화 로그/계정/새 모델/API 실행으로 데이터를 만들지 않았다.

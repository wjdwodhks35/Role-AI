# Coding Agent 성능·안정성 개선 보고서 (2026-10-28 KST)

## 1. 기존 문제 및 원인

기준선은 PR #30 커밋 `38d4d14`이다. 최신 dev `babb0fa`에서 별도 worktree/feature 브랜치를 만든 뒤 PR #30의 선행 커밋을 로컬 cherry-pick했다. 개발 원본과 기존 벤치마크 worktree의 미커밋 파일은 보존했다.

- 컨텍스트 구성은 일부 필드만 제거해 16,000자 상한을 보장하지 못했다. 유효한 길이의 목표·계획·경로와 누적 진행 기록을 조합하면 30,399자를 반환했다.
- 동일 내용 패치가 workspace의 무변경/해시 거부에 걸린 뒤 일반 도구 실패로 종료됐다. 17/19번 과제 응답의 합성 재생에서 재현했다.
- 응답 1,500자 절단 후 JSON·patch 지표를 계산하던 평가 오류가 있었다.
- 첫 개선 후보(V1)는 간결해진 지침과 중복된 계획/관찰 때문에 패치 뒤 테스트 대신 계획을 반복하는 실제 회귀가 관찰됐다. 이를 좋은 변경으로 분류하지 않았다.
- 사용자 요청으로 실모델 실험을 68회 완료 후 중단했다. 진행 중 호출과 이 작업의 전용 Ollama 프로세스도 종료했으며, 이후 실모델 테스트는 수행하지 않았다.

| `coding_edits.py` | 문자열 리터럴의 이스케이프 보존, 애매한 f-string 변환 거부, 정규화 시도 코드, 중복 행의 유사도 점수 재사용 |
| `qa/bench_coding_models.py` | 전체 응답 분석, 실제/미측정 구분, 출력·context 옵션, all-skipped 거부 |

자동 테스트는 새 작업을 승인할 때 저장된 정책에만 적용한다. 기존 작업은 원래 명시적 테스트 방식이며, 원래 테스트 스위트의 호출 횟수 검증도 legacy 옵션으로 보존했다. 새 기본 동작은 별도 테스트로 검증했다. 테스트 러너·파일 범위·승인·command/step/time 예산을 우회하지 않고, 자동 테스트 직전 pending/container를 원자적으로 저장한다. 동일 revision의 성공/실패 증거만 재사용하며 코드가 바뀌면 다시 실행한다. passing 증거 없는 completed는 허용하지 않는다.

## 3. 테스트 및 회귀 검사 결과

- 최종 Excel QA: **323개 시나리오, 582회 모두 통과**, 계획 순서 일치, 144.92초.
- 코딩 관련 이전 단계 80개 통과 후 추가 원인 보존·cache 무효화 검사까지 전체 QA에서 통과했다.
- Ruff 및 `git diff --check` 통과. 기존 테스트 삭제/보안 약화 없음.
- 자동 테스트 검증은 모의 의사결정 + 임시 합성 저장소의 실제 `unittest` 실행이다. LLM/Ollama 서버는 호출하지 않았다.
- 실제 Docker 경로는 소켓 권한 제약으로 미검증이다. production의 Docker 전용 실행 정책은 그대로 유지한다.

## 4. 모델별·조건별 성공률 — 수정 전 V1의 중단 실험

다음 표는 **최종 코드의 실모델 성적이 아니다**. 회귀가 발견된 첫 후보의 동결 결과다. 같은 RTX 4060 Ti 8GB/Ollama 0.40.12, 모델 digest·온도 0·num_ctx 4096·출력 1,024/호출·60초 제한·host-runner를 사용했다. 과제별 2회이며 두 번째 반복은 기준선/후보 순서를 반전했다. 반복이 적고 결정적 모델의 상관성이 있어 통계적 우위를 주장하지 않는다.

| 모델 | 버전 | 성공 | 전체 평균 | 성공 작업 평균 | 성공 작업당 실측 토큰 평균 |
|---|---|---:|---:|---:|---:|
| qwen3.5:4b | 기준선 | 6/10 | 15.7초 | 9.0초 | 4,508 |
| qwen3.5:4b | V1 후보 | 2/10 | 15.3초 | 15.2초 | 7,278 |
| qwen3:8b | 기준선 | 6/10 | 13.3초 | 13.7초 | 6,016 |
| qwen3:8b | V1 후보 | 6/10 | 29.4초 | 13.2초 | 4,142 |

기준선 12/20(60%) → V1 8/20(40%). 성공한 과제 구성이 달라 토큰 평균 차이를 순수 효율 개선으로 볼 수 없다. 양쪽 모두 성공한 동일 과제/반복 6쌍의 평균 시간도 기준선 9.43초 → V1 13.88초로 악화됐다.

T3·T5에 한정한 설정별 결과:

| 조건 | qwen3.5 성공/실행 | 평균 시간 | qwen3:8b 성공/실행 | 평균 시간 |
|---|---:|---:|---:|---:|
| V1 기본값 | 0/4 | 16.9초 | 2/4 | 40.4초 |
| Thinking ON | 2/4 | 55.8초 | 0/4 | 90.5초 |
| keep_alive=0 | 0/4 | 48.1초 | 2/4 | 99.0초 |
| 정규화 OFF | 0/4 | 15.4초 | 2/4 | 41.2초 |
| 구 컨텍스트 — 부분 실행 | 1/2 | 26.4초 | 2/2 | 16.4초 |

104회 설계는 기본 paired 40회 + 단일 구성요소 비교 48회 + holdout 16회였다. **68회 완료**, 구 컨텍스트 반복 중 사용자 지시로 중단했다. 나머지 구 복구/출력 2,048/holdout은 실행하지 않았다. 중단한 시도와 private 체크포인트/원본 로그도 로컬에 보존했다. holdout 성공률이나 최종 코드 성공률을 만들지 않았다. 구 컨텍스트는 프롬프트와 구성 정책을 함께 되돌리는 component 비교이며, 부분 결과만으로 특정 하위 변경의 인과관계를 확정하지 않는다.

## 5. 실행 시간과 토큰 효율 — 최종 코드의 모델 없는 비교

같은 합성 목표와 실제 unittest 통과 기준을 사용했다. 의사결정은 Scripted 모델이며 실측 LLM 토큰은 없다.

| 항목 | 기준선 | 최종 코드 | 확인된 차이 |
|---|---:|---:|---|
| 계획→패치→테스트→완료의 모델 요청 | 4회 | 3회 | 필수 테스트 요청 한 번 제거(25%) |
| 동일 흐름 tool step | 4 | 4 | 승인된 step 예산은 그대로 소비 |
| 동일 흐름 실제 unittest 실행 | 1회 | 1회 | passing 증거 유지 |
| 모의 흐름의 예약 토큰 | 20,480 | 15,360 | 실측 사용량/실모델 토큰 절감 주장이 아님 |
| 같은 revision에 테스트 2회 요청 시 러너 실행 | 2회 | 1회 | 기존 실행 결과 재사용, 코드 변경 시 무효화 |

CPU 마이크로벤치마크: 준비 3회 후 50회, 100,024바이트 합성 입력(중복 행 포함), 같은 호스트. CPU 부하는 완전히 통제하지 않았고 전체 서비스 속도 측정이 아니다.

| 항목 | 기준선 중앙값 | 최종 코드 중앙값 |
|---|---:|---:|
| 정확 일치 패치 | 0.0369ms | 0.0392ms |
| 불일치 유사 코드 탐색 | 78.9484ms | 1.3244ms |
| 긴 상태의 컨텍스트 | 30,399자 | 12,573자 |

목표는 그대로 보존했다. 본문 문자 제한과 모델 입력 토큰 bound를 구분하며, 실제 토큰은 응답이 측정한 경우에만 정산한다. 입력 사전 계수는 byte-level tokenizer용 보수적 UTF-8 bound와 framing 여유이며 정확한 tokenizer 결과를 가장하지 않는다. 모델별 정확 사전 토큰화는 남은 한계다.

## 6. 개선이 확인된 부분

필수 테스트에 쓰는 모델 요청 제거, 불변 revision의 중복 테스트 실행 제거, 안전한 no-op 복구, 멱등 정산과 실행 불명 시 예약 보존, 목표/원문을 보존하는 컨텍스트 상한, 반복 행의 유사 코드 탐색 비용 감소를 코드/CPU 테스트로 확인했다. 새로운 무거운 의존성이나 추가 LLM/압축 모델은 도입하지 않았다.

## 7. 개선되지 않았거나 악화된 부분

V1의 실모델 성공률은 낮아졌고, 같은 성공 과제의 시간도 악화됐다. 이 후보를 개선 성공으로 포장하지 않았다. 이후 계획 상태 보존/중복 제거/명확한 JSON 지침/자동 테스트로 구조를 수정했으나, 사용자 요청에 따라 **최종 코드의 실모델 성능은 재측정하지 않았다**.

## 8. 남은 문제

최종 모델별 성공률, Docker 실기, 모델별 정확한 사전 토큰화, 충분한 독립 평가 표본, 일부 복잡한 패치/모델 반복 행동은 미확인이다. 오래된 상세 관찰은 기존 private 체크포인트 보관 범위의 제약이 있다. raw 예외/운영 비밀은 공개 로그에 넣지 않고 코드/단계/예외 타입으로 구분한다. keep_alive 기본값은 300초이며 GPU admission 정책 강제 0과 작업 종료 후 해제 정책은 유지했다.

## 9. 다음 검증 추천 / 재현

현재 추가 모델 실험은 하지 않는다. 추후 사용자가 요청하면 104회 전체보다 회귀가 났던 T1/T3/T5의 작은 paired 비교부터 확인하고, 별도 과제를 최종 평가로 남긴다.

```bash
PYTHONPATH=. .venv/bin/python qa/run_excel_tests.py
PYTHONPATH=. .venv/bin/python qa/check_coding_workflow.py --out qa/results/workflow.json
PYTHONPATH=. .venv/bin/python qa/bench_coding_cpu.py --out qa/results/cpu.json
```

원시 합성 결과/환경/해시/동결 V1 소스 patch·평가 스크립트는 `qa/reports/coding-upgrade-20261028/`에 있다. V1을 재구성하려면 `38d4d14` 기반 별도 checkout에 `git apply --unidiff-zero measured-v1-runtime.patch`를 적용하고 `measured-v1-evaluator/*.txt`의 확장자를 복원해 qa 파일로 사용한다. 모형화된 의사결정의 예약 토큰과 실제 모델 토큰을 섞지 않는다.

평가 설계 참고: [Anthropic의 에이전트 평가 설계](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)는 실제 결과·전사·회귀 과제 보존을, [OpenAI의 SWE-bench 신뢰성 분석](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)은 요구사항과 채점의 일치·평가 누출 방지를 참고했다. [Ollama Chat API](https://docs.ollama.com/api/chat)의 thinking 지원 값과 duration/token 필드를 실제 모델 metadata와 대조했다.
